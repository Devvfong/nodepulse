# ADR 005: Server-Sent Events (SSE) for Real-Time Metrics Streaming

## Status
Accepted

## Date
2026-10-06

## Context
Monitoring dashboards, live CLI displays, and operators frequently require high-frequency, continuous system telemetry (e.g. 1-second metric pulses for CPU, memory, and network throughput).

Two primary architectural approaches exist:
1. **Aggressive Client Polling**: Clients issue rapid, sequential HTTP GET requests (e.g. every second).
2. **Persistent Streaming**: A single TCP connection is established over which the agent pushes live updates.

Frequent polling incurs significant HTTP header parsing overhead, TCP socket churn, and higher CPU utilization on both the agent and the host.

## Decision
We adopt **Server-Sent Events (SSE)** over HTTP/1.1 via `GET /api/v1/events` as the standard real-time streaming mechanism.

## Consequences

### Positive
- **Standard HTTP/1.1 Protocol**: Operates over standard HTTP connections (`Content-Type: text/event-stream; charset=utf-8`) without custom framing or protocol negotiation.
- **Browser & CLI Native**: Supported out-of-the-box by browser `EventSource` APIs and standard CLI tools (`curl -N -H "X-API-Key: ..." http://host/api/v1/events`).
- **Unidirectional Alignment**: NodePulse is a read-only monitoring agent. The unidirectional nature of SSE (server to client) perfectly matches the telemetry streaming use case.
- **Lightweight Connection Lifecycle**: Drogon's non-blocking chunked response mechanism handles active SSE clients on the epoll loop without dedicating threads to idle connections.
- **Automatic Reconnection**: The SSE protocol provides native reconnection and event ID tracking.

### Negative / Trade-Offs
- **Unidirectional Only**: Clients cannot send control messages back upstream over the SSE connection (separate REST calls must be used).
- **Connection Limits**: Standard HTTP/1.1 limits persistent concurrent connections per host domain in some browsers (mitigated by HTTP/2 or dedicated monitoring hostnames).

## Alternatives Considered
- **WebSockets (RFC 6455)**: Bidirectional, but requires custom handshake, framing, ping/pong pingers, and stateful socket management. Bidirectional communication is unnecessary for a read-only agent.
- **gRPC Server Streaming**: Efficient binary protocol, but requires heavy Protobuf toolchains and runtime libraries, and cannot be consumed directly by simple `curl` commands or basic browser web pages without gRPC-Web proxies.
- **Short Polling**: Simpler to implement initially, but wastes bandwidth and CPU resources under continuous live monitoring.
